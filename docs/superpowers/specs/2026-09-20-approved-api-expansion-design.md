# 달빛수원 승인 API 관리·수집·검수 확장 설계

- 작성일: 2026-09-20
- 상태: 설계 승인 완료, 구현계획 작성 전
- 대상 저장소: `moon_suwon`
- 관련 앱: [ChoiKkang/MoonSuwonApp](https://github.com/ChoiKkang/MoonSuwonApp) — 이 작업에서는 앱 저장소를 수정하지 않는다.

## 1. 목적

공공데이터포털에서 승인받은 14개 API를 한 곳에서 관리하고, 아직 연결되지 않은 9개 API를 달빛수원의 기존 `raw → core → public` 파이프라인에 추가한다. 수집 성공과 서비스 공개를 분리해 원문은 보존하되, 앱에는 지역·품질·신선도 검사를 통과한 데이터만 기존 계약을 깨지 않는 형태로 제공한다.

운영계정 전환은 공모전 접수 과정에서 이미 처리되었으므로 이 작업의 범위가 아니다. 다만 관리대장에는 운영계정 처리 상태와 만료일을 기록한다.

## 2. 현황과 정확한 범위

승인 API는 14개이고, 현재 코드에 연결된 승인 API 상품은 5개다. 동기화 작업은 6개인데, 국문 관광정보 서비스 안에서 일반 콘텐츠와 행사를 별도 작업으로 실행하기 때문이다.

### 현재 연결된 승인 API

1. 국문 관광정보 서비스
2. 무장애 여행 정보
3. 관광지 오디오 가이드정보
4. 관광지 집중률 방문자 추이 예측 정보
5. 반려동물 동반여행 서비스

### 새로 연결할 승인 API

1. 관광사진 정보
2. 웰니스관광정보
3. 기초지자체 중심 관광지 정보
4. 경기도 버스도착정보 조회
5. 기상청 단기예보 조회서비스
6. 기상청 중기예보 조회서비스
7. 두루누비 정보 서비스
8. 관광지별 연관 관광지 정보
9. 빅데이터 지역별 방문자수

## 3. 설계 원칙

1. 앱은 원천 API를 직접 호출하지 않는다. API 키와 Supabase service role은 서버 및 GitHub Actions에만 둔다.
2. 모든 원문은 `raw`에 저장하고, 앱이 사용하는 의미와 단위는 `core`에서 정규화한다.
3. 공개 계약은 additive 변경을 사용한다. 기존 RPC 이름과 기존 JSON 필드의 의미를 바꾸지 않는다.
4. 수집됐다는 사실만으로 장소·사진·코스를 자동 공개하지 않는다.
5. 원천이 정상적으로 0건을 반환한 경우 성공한 빈 결과로 기록하고 장애로 취급하지 않는다.
6. 마지막 정상 데이터는 새 실행이 실패해도 삭제하지 않고 `stale` 상태로 남긴다.
7. 수원 네 개 구는 `41111`, `41113`, `41115`, `41117`을 공통 상수로 순회한다. 상위 코드 `41110`의 정상 0건 응답을 수원 데이터 부재로 오판하지 않는다.
8. 원천의 설명과 HTML은 데이터로만 처리하며 실행하거나 신뢰하지 않는다.

## 4. 전체 구조

```text
공공데이터포털 API
  → 공급자별 TypeScript 클라이언트
  → raw 원문·동기화 실행·오류 기록
  → core 정규화·지역 매칭·장소 연결
  → 자동 품질검사 또는 관리자 검수
  → public 읽기 전용 RPC/view
  → 달빛수원 앱·홍보 웹

raw.sync_runs + API 관리대장
  → 관리자 운영 상태 화면
  → 신선도·수집량·공개량·오류·검수 대기 표시
```

기존 `raw.sync_runs`, `raw.sync_errors`, `core.places`, `editorial.place_publish_state`와 공개 RPC 경계를 재사용한다. 신규 테이블은 private schema에 두고, 공개 앱에는 필요한 필드만 `security_invoker` 뷰 또는 공개 RPC로 제공한다.

## 5. 14개 API 관리대장

`ops.api_registry`를 관리대장의 기준 데이터로 사용한다. 14개 행은 마이그레이션에서 안정된 `api_key`로 seed하고 이름 변경에도 동일한 키를 유지한다.

관리 필드는 다음과 같다.

| 필드 | 의미 |
| --- | --- |
| `api_key` | 코드와 동기화 로그가 사용하는 불변 식별자 |
| `provider` | 한국관광공사, 기상청, 경기도 |
| `display_name` | 관리자 화면 표시 이름 |
| `approval_status` | 승인 상태 |
| `account_stage` | 개발, 운영전환접수, 운영 |
| `approved_at`, `expires_at` | 승인일과 만료일 |
| `implementation_status` | 미구현, 구현, 활성, 보류 |
| `sync_job` | 연결된 동기화 작업 이름 |
| `schedule_label` | 사람이 읽는 실행 주기 |
| `freshness_sla_hours` | 신선도 판정 기준 |
| `review_policy` | 자동 공개, 검수 후 공개, 내부 분석, 원문 전용 |
| `last_reviewed_at`, `review_note` | 운영 검수 결과 |

실행 시각, 수집량, 적재량, 오류 수는 중복 저장하지 않고 최신 `raw.sync_runs`를 조합해 표시한다. 이를 통해 대장의 설정 정보와 실행 로그가 서로 어긋나지 않게 한다.

관리자 운영 화면은 API별로 다음 상태를 보여준다.

- 승인·계정·만료 상태
- 구현·스케줄 상태
- 마지막 성공 및 실패 시각
- 마지막 수집·변경·공개 건수
- 신선도와 SLA 초과 여부
- 검수 대기 수와 최근 검수 메모
- 정상 0건, 쿼터 중단, 인증 실패, 지역 코드 오류의 구분

## 6. 원문과 정규화 모델

### 6.1 공통 원문 저장소

서로 다른 API 응답을 일관되게 추적하기 위해 `raw.public_api_items`에 다음 공통 열을 둔다.

- `api_key`
- `source_item_key`
- `scope_key` — 구 코드, 격자, 정류소, 기준월 등 호출 범위
- `source_updated_at`
- `fetched_at`
- `payload jsonb`
- `payload_hash`
- `last_sync_run_id`

유일 키는 `(api_key, source_item_key, scope_key)`로 한다. 동일 원문은 hash 비교로 변경 없음과 실제 변경을 구분한다. 데이터셋별 검색과 앱 계약은 JSON을 직접 조회하지 않고 `core` 정규화 테이블을 사용한다.

### 6.2 정규화 데이터

| API | core 모델 | 공개 용도 |
| --- | --- | --- |
| 관광사진 | 장소 연결 이미지 후보, 저작권·촬영자·출처 | 검수 승인된 장소 이미지 |
| 웰니스 | 수원권 웰니스 장소 후보 | 검수 승인된 장소 태그·설명 |
| 기초지자체 관광지 | 기준월별 관광지 후보·지표 | 관리자 추천 후보 |
| 연관 관광지 | 출발·도착 장소 관계와 원천 점수 | 주변/다음 관광지 추천 |
| 두루누비 | 수원과 공간적으로 교차하는 코스 | 검수 승인된 외부 코스 참고 |
| 지역별 방문자수 | 구·일자·방문자 구분별 집계 | 관리자 월별·요일별 분석 |
| 단기예보 | 격자·예보시각·대상시각·항목·값 | 장소/코스 날씨 요약 |
| 중기예보 | 권역·발표시각·예보일·날씨·기온 | 여행계획용 전망 |
| 버스도착 | 정류소·노선·도착 순번·예상시간 | 매핑된 장소의 교통 정보 |

## 7. API별 수집과 공개 정책

### 7.1 관광사진

- `수원` 검색 결과를 페이지 끝까지 수집한다.
- 제목, 장소명, 주소, 좌표를 기존 장소와 정규화해 연결한다.
- 저작권 구분, 촬영자, 원본 출처, 이미지 URL이 없는 항목은 공개 후보에서 제외한다.
- 자동으로 기존 대표 이미지를 교체하지 않는다.
- 주소가 수원시이고 장소 일치가 명확한 항목만 검수 승인한다.
- 공개 시 출처와 저작권 필드를 이미지 계약에 함께 제공한다.

### 7.2 웰니스관광정보

- 수원 중심 좌표와 반경으로 발견한 뒤 실제 주소·좌표가 수원 또는 인접 생활권인지 확인한다.
- 기존 장소와 일치하면 웰니스 태그 후보로 연결하고, 새로운 장소는 검수 후보로만 저장한다.
- 수원 외 항목은 원문에 남기되 앱 공개 대상에서 제외한다.

### 7.3 기초지자체 중심 관광지와 연관 관광지

- 최신 제공 기준월을 먼저 확인하고 수원 네 개 구를 모두 순회한다.
- 기준월과 구 코드별 0건 여부를 기록하며, 일부 구만 0건이면 경고한다.
- 연관 관광지는 양 끝 장소가 모두 공개 장소와 연결될 때만 앱 후보가 된다.
- 원천 관계 점수만으로 자동 추천하지 않고 거리, 야간 운영, 공개 상태, 좌표를 함께 검증한다.
- 앱 공개 RPC는 기존 장소 상세에 `related_places`를 additive 필드로 제공한다.

### 7.4 두루누비

- 전체 코스 원문을 수집하고 제목 검색만으로 수원 여부를 판단하지 않는다.
- 코스 좌표·경로가 수원 경계와 교차하거나 주소가 수원인 항목만 검수 후보로 만든다.
- 조건을 만족하는 항목이 0건이면 정상 0건으로 관리대장에 표시하고 앱에는 빈 목록을 제공한다.

### 7.5 지역별 방문자수

- 원천이 전국 데이터를 반환하므로 월 단위로 페이지를 수집한 뒤 수원 네 개 구만 추출한다.
- 일별·지역별 원문을 월별/요일별 내부 분석 테이블로 집계한다.
- 방문자 수를 실시간 관광객이나 혼잡도로 표현하지 않는다.
- 장소 상세가 아닌 관리자 분석과 향후 추천 가중치에 사용한다.

### 7.6 단기·중기 기상예보

- 단기예보는 수원 격자 `nx=60`, `ny=121`을 기준으로 최신 발표를 수집한다.
- 기온, 강수확률, 강수형태, 강수량, 풍속, 하늘상태를 시간대별로 정규화한다.
- 앱에는 현재부터 야간 관광 시간대까지의 요약과 `generated_at`, `forecast_at`, `data_status`를 제공한다.
- 중기예보는 수도권 권역을 수집해 4~11일 여행계획 데이터로만 사용한다.
- 오래된 발표 자료는 마지막 정상값과 함께 `stale`로 표시한다.

### 7.7 버스도착정보

- 승인된 도착정보 API는 정류소 ID가 있어야 호출할 수 있으므로 `core.place_bus_stops`에 검수된 장소–정류소 매핑을 둔다.
- 초기에는 확인 가능한 수원 대표 정류소를 등록하고, 매핑 근거와 검수 시각을 저장한다.
- 매핑되지 않은 장소에는 임의 정류소를 추정하지 않는다.
- 도착정보는 장기 보존용 콘텐츠가 아니므로 짧은 TTL 캐시와 최신 스냅샷만 유지한다.
- 앱 공개 RPC에는 정류소명, 노선, 예상 도착 초, 남은 정류장 수, 조회 시각을 제공한다.
- 정류소 검색 권한이나 신뢰할 수 있는 정류소 목록을 확보하지 못한 장소는 보완 대상으로 남긴다.

## 8. 동기화 작업과 주기

기존 6개 작업에 신규 작업을 추가하되 공급자별 호출 압력을 분산한다.

| 작업 | 주기 | 최대 허용 신선도 |
| --- | --- | --- |
| `weather_short` | 3시간마다 | 6시간 |
| `weather_mid` | 하루 2회 | 18시간 |
| `bus_arrival` | 앱용 서버 캐시 또는 2분 단위 요청 시 갱신 | 5분 |
| `photo` | 주 1회 | 8일 |
| `wellness` | 주 1회 | 8일 |
| `local_hub` | 월 1회, 기준월 변경 시 | 45일 |
| `related` | 월 1회, 기준월 변경 시 | 45일 |
| `durunubi` | 주 1회 | 8일 |
| `visitors` | 월 1회, 직전 확정월 | 45일 |

버스 도착정보는 GitHub Actions로 전국 정류소를 주기 수집하지 않는다. 앱 요청을 받은 서버가 검수된 정류소만 조회하고 2분 캐시를 공유하도록 한다. 나머지 작업은 GitHub Actions 수동 실행, `--dry-run`, `--limit`을 지원하며 `--limit`은 모든 작업에서 실제 상류 호출과 적재 건수를 제한해야 한다.

## 9. 상태 검증과 관측성

`data:verify`는 14개 API 관리대장과 모든 활성 동기화 작업을 검사한다.

### 공통 검사

- 최근 실행 존재 여부
- 성공/부분성공/실패/쿼터중단 상태
- SLA 초과
- 인증·등록되지 않은 키·트래픽 초과 오류
- 0건 응답과 전회 대비 급감
- fetched, unchanged, changed, upserted, published, zero_result 분리
- 중복 원천 키와 payload hash 충돌
- raw/core/public 건수의 비정상 역전

### 데이터셋별 검사

- 관광사진: 수원 주소 비율, 저작권 정보 누락, 깨진 URL
- 웰니스·관광지 후보: 수원 경계, 좌표, 기존 장소 중복
- 연관 관광지: 양 끝 장소 존재·공개 상태, 자기 자신 관계, 중복 관계
- 두루누비: 수원 교차 코스 수와 정상 0건 구분
- 방문자수: 기준월 완결성, 네 개 구 누락, 음수·중복 집계
- 날씨: 발표시각, 예보 시간 연속성, 필수 항목 누락
- 버스: 정류소 매핑 근거, 캐시 나이, 조회시각, 음수 도착시간

관리자 화면과 Discord 요약은 실패뿐 아니라 검수 대기, 일부 구 0건, 커버리지 급감도 구분해 알린다.

## 10. 반려동물 커버리지 개선

반려동물 동기화 메타데이터를 다음 단계로 분리한다.

- `discovered_count`
- `detail_attempted_count`
- `detail_success_count`
- `source_empty_count`
- `policy_valid_count`
- `unchanged_count`
- `changed_count`
- `upserted_count`
- `published_covered_count`

공개 장소 중 아직 상세조회를 하지 않은 장소, 오래된 장소, 직전 네트워크 실패 장소를 우선순위 큐로 다시 조회한다. 성공한 빈 결과는 `unavailable`, 네트워크 실패는 기존 값을 유지한 `stale`, 유효 정책은 `fresh`로 구분한다. 수동 override는 자동 수집이 덮어쓰지 않는다.

커버리지 목표는 API에 실제 원천 정보가 있는 장소를 모두 연결하는 것이다. 원천이 제공하지 않는 45개 장소를 임의로 `allowed` 또는 `not_allowed`로 추정해 숫자만 높이지 않는다.

## 11. 혼잡도 커버리지 개선

- 수원 네 개 구의 전체 페이지를 수집하고 `tAtsNm`을 정규화한 이름·주소·좌표 후보와 매칭한다.
- 자동 매칭은 단일 고신뢰 후보만 허용하고, 다중 후보와 미매칭은 검수 큐에 넣는다.
- 오늘 예보뿐 아니라 향후 예보 범위의 연속성과 공개 장소 연결률을 기록한다.
- `matched_place_count`, `unmatched_attraction_count`, `published_covered_count`, `forecast_date_count`를 실행 메타데이터에 저장한다.
- 공개 문구는 상대 집중률 예측임을 유지하고 실시간 인원 또는 실시간 혼잡도로 표현하지 않는다.

## 12. 검수 정책

이번 초기 적재의 데이터 검수는 구현 담당 에이전트가 수행하고 결과를 보고한다.

### 자동 승인 가능한 데이터

- 단기·중기 날씨: 공식 응답, 예상 범위, 시각 연속성, 필수 항목 검사 통과
- 방문자 통계: 수원 네 개 구, 기준월 완결성, 중복 제거 검사 통과
- 버스 도착: 검수된 정류소 매핑에 대한 정상 최신 응답

### 항목별 검수 후 승인하는 데이터

- 관광사진: 장소 연결, 수원 지역, 출처·저작권·URL 검사
- 웰니스: 주소·좌표·관광 적합성·기존 장소 중복 검사
- 기초지자체 관광지: 지역·좌표·기존 장소 연결·야간 관광 적합성 검사
- 연관 관광지: 양 끝 공개 장소, 거리, 운영시간, 자기 관계·중복 검사
- 두루누비: 수원 경계 교차, 경로·명칭·출처 검사

검수 결과는 승인, 보류, 제외로 기록한다. 제외된 원문은 삭제하지 않고 제외 이유와 검수 시각을 보존한다. 앱에는 승인된 데이터만 공개한다.

## 13. 공개 앱 계약

앱 저장소는 수정하지 않는다. 웹 저장소에서 다음 additive 계약을 준비하고 fixture와 예시를 문서화한다.

- 장소 상세: `related_places`, `approved_photos`, `wellness_tags`, `weather_summary`, `nearby_bus_arrivals`
- 운영 상태: 각 블록에 `data_status`, `source_updated_at`, `fetched_at`
- 관리자 전용: 방문자 추세, 후보와 검수 상태

신규 필드는 데이터가 없을 때 빈 배열 또는 `null`을 반환하고 기존 필드를 제거하지 않는다. 앱 담당자가 준비되기 전에도 기존 버전은 그대로 작동해야 한다.

## 14. 보안

- 원천 API 키, service role, 전체 민감 요청 URL을 로그나 브라우저에 노출하지 않는다.
- `raw`, `core`, `ops`는 anon/authenticated에 직접 공개하지 않는다.
- 공개 뷰는 `security_invoker = true`를 사용하고 RLS/권한을 명시한다.
- 공개 RPC는 공개·활성 장소와 승인된 데이터만 반환한다.
- 내부 sync RPC는 `service_role`만 실행할 수 있게 `PUBLIC`, `anon`, `authenticated` 실행 권한을 회수한다.
- 신규 공개 테이블에 대한 Data API 자동 노출에 의존하지 않고 명시적으로 grant/revoke한다.

## 15. 테스트와 검증

### 단위 테스트

- 공급자별 응답 파싱과 빈 items 처리
- 페이지네이션과 `--limit`
- 수원 구 코드 순회
- 원천 키·scope key·hash 안정성
- 날짜·기상 단위·버스 도착값 정규화
- 지역·좌표·중복·저작권 검수 판정
- 반려동물과 혼잡도 메트릭 분리

### DB·계약 검증

- 재실행 idempotency
- raw/core/public 개수와 연결 무결성
- 앱 공개 RPC의 기존 필드 하위 호환
- 비공개·미검수 데이터 차단
- anon 사용자의 private schema 접근 거부
- service-role 전용 sync RPC 권한

### 실데이터 검수

1. 모든 신규 작업을 작은 `--limit` dry-run으로 확인한다.
2. 전체 수집을 실행하고 API별 fetched/changed/upserted/zero 결과를 확인한다.
3. 수원 지역, 좌표, 중복, 저작권, 시간 범위를 샘플과 전수 규칙으로 검사한다.
4. 승인 기준을 통과한 항목만 공개한다.
5. anon 키로 공개 RPC를 호출해 앱에 필요한 데이터만 반환되는지 확인한다.
6. 전체 테스트, 타입 검사, lint, 빌드, 데이터 상태 검사를 실행한다.

## 16. 완료 기준

1. 관리자 운영 화면에서 승인 API 14개가 빠짐없이 표시된다.
2. 활성 API마다 최근 실행, 수집량, 오류, SLA, 검수 상태를 확인할 수 있다.
3. 신규 9개 API가 실제 호출되고 원문과 정규화 데이터가 저장된다.
4. 수원 데이터가 없는 API는 정상 0건으로 식별되며 장애와 구분된다.
5. 반려동물과 혼잡도의 수집 단계 및 공개 커버리지 지표가 분리된다.
6. 날씨·연관 관광지·검수 이미지·매핑된 버스 정보가 공개 앱 계약으로 제공된다.
7. 방문자 통계는 관리자 분석으로 제공되고 실시간 혼잡도로 오해되지 않는다.
8. 비공개, 수원 외, 중복, 출처 불명, 오래된 데이터가 앱에 노출되지 않는다.
9. 앱의 기존 RPC 소비 방식과 기존 필드가 깨지지 않는다.
10. API 키와 private schema가 앱 또는 익명 사용자에게 노출되지 않는다.

## 17. 구현 순서

1. 14개 API 관리대장과 공통 원문 저장·권한 구조
2. 공급자별 클라이언트와 순수 정규화/검수 모듈
3. 관광사진·웰니스·기초지자체·연관 관광지·두루누비 수집
4. 방문자 통계와 기상예보 수집
5. 버스 정류소 매핑과 짧은 캐시 기반 도착정보
6. 반려동물·혼잡도 메트릭 및 재조회 개선
7. 전체 동기화 상태 검증과 관리자 관리대장 UI
8. 공개 RPC·fixture·앱 전달 문서
9. 실데이터 전체 적재와 구현 담당 에이전트의 검수·승인
